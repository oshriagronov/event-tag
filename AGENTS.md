# Agent Context: EventTag (Private Selfie-Based Cloud Event Photo Sharing Web App)

You are an expert Frontend Engineer and Client-Side Machine Learning specialist. Your role is to help develop **EventTag**, a privacy-first web application designed to scan event photos loaded directly from cloud storage (Dropbox & Google Drive active; OneDrive marked as "Soon") so guests can instantly retrieve their personal photos using a selfie in the easiest and most private way possible, with face descriptors synced securely in the cloud.


## Project Core Concept & Goal
- **What it is:** A web application where event organizers connect photos from cloud storage (Dropbox & Google Drive active; OneDrive coming soon), and the browser automatically scans, detects, and encodes faces locally. Guests can then scan a QR code / share link and upload a selfie to instantly retrieve all photos they appear in.
- **The Goal:** Make photo sharing between event organizers and guests as seamless, instant, and private as possible. Event organizers connect and scan their cloud photo folders, while guests self-service retrieve and download their personal event photos using a selfie.
- **The Ultimate Constraint:** **Cloud Ingest with Local Processing.** Images are read directly from cloud storage or local disk into browser memory, all face detection and descriptor extraction happens locally in the user's browser, and only mathematical face descriptors are stored in Firebase Firestore (readable only by the event owner). Guest matching compares the selfie's descriptor server-side in `api/match.ts` (never the selfie image; nothing is stored). No actual photo files are uploaded to or stored on our servers.

## Core Development Rules & Guidelines

### 1. Storage Architecture (Cloud-Only & Privacy-First)
- EventTag supports **Cloud Events only**.
- All photos are ingested on-the-fly from cloud providers (Google Drive / Dropbox) directly into browser memory.
- **Persistent Cloud Provider Connections:** Provider state remains active until the user explicitly clicks "Disconnect" ("נתק"). Dropbox uses PKCE/offline renewal through `api/dropbox-token.ts`. Google uses the GIS authorization-code popup flow (when `VITE_GOOGLE_OFFLINE_ACCESS=true`) through `api/google-token.ts` (holds `GOOGLE_CLIENT_SECRET`). Both brokers keep the refresh token only in an encrypted, uid-bound HttpOnly cookie (never in browser storage; refresh tokens left in localStorage by older builds are migrated once via `legacy_refresh_token` and deleted) and revoke the grant on disconnect. Access tokens of broker-backed providers live in `sessionStorage` (per tab); OneDrive and non-broker Google keep theirs in localStorage. Without a deployed broker (plain Vite dev server), Dropbox falls back to the browser-only PKCE flow and Google to 1-hour GIS tokens with best-effort silent renewal. Neither flow displays a popup automatically. All provider calls obtain tokens through `AuthContext.getFreshAccessToken(provider, { rejectedToken })`, which renews tokens 5 minutes before expiry and dedupes concurrent renewals. Only an explicit invalid/revoked-token response may clear an access token. Network, quota, timeout, missing-file, and authorization/scope failures retain the connection and surface their own recoverable error states.
- All metadata, image file references, face descriptors, and clusters sync to Firebase Firestore. No photo binaries are ever uploaded to backend servers.
- **OAuth Redirect Safety:** Implicit-flow redirects (Google fallback, OneDrive) are only accepted when the returned `state` matches the one-time value stored in `sessionStorage` before redirecting (`createOAuthState`); Dropbox tokens are never read from the URL (PKCE code flow only). Never accept tokens from the URL without state validation, since a planted token would route a user's uploads into an attacker's cloud account.
- **Untrusted Photo Links:** Photo documents (`publicUrl`, `fileName`, file IDs) are written by event owners and shown on public guest pages. Always pass them through `convertToRawUrl` / `toTrustedPhotoUrl` / `isValidDriveFileId` (`cloudProviders.ts`), which drop anything but https URLs on known provider hosts, and sanitize file names before using them in downloads or ZIP entries.
- **Account Deletion & Data Purge:** When a user deletes their account, all associated Firestore events and subcollections (`photos`, `faceBatches`) are deleted, the `users/{uid}` profile and its `usage` document are deleted in one batch (`deleteUserData`), cloud provider OAuth tokens and persistent connections are disconnected, active scanning loops are cancelled, client-side storage & IndexedDB are wiped, Firebase Auth user account is deleted, and privacy consent is completely reset (`resetConsent()`) so the consent banner is re-triggered on next visit/login.

### 2. Ingest Performance & Memory Safety
- **Image Downscaling:** To prevent WebGL out-of-memory crashes and speed up inference, images must be conditionally downscaled to a maximum dimension of `1600px` using an offscreen canvas prior to passing to `face-api.js` (implemented in scanning workflow).
- **Sequential Ingestion:** Never keep multiple full-res images in memory simultaneously. Face processing runs through `withComputeLock` in `ScannerContext` (one photo at a time across all workers and events); upload workers (Google 4, Dropbox 3) only add uploads in flight. Cloud scans prefetch 4 photo blobs and share links ahead. Revoke object URLs immediately after processing.
- **Background-Tab Safety:** `installBackgroundSafeReadback()` (`faceDetection.ts`, called by `ensureModelsLoaded`) switches tfjs WebGL readback to synchronous mode while the tab is hidden, since Chrome throttles the timer-based GPU polling in background tabs. Keep it when changing the tfjs backend setup.
- **Firestore Write Buffering:** Photo documents and face descriptors are buffered in memory and committed atomically with `commitScanResults`, which posts each chunk to `/api/commit-scan` (one transaction, every 15 photos or 50 faces; `addCloudPhotosBatch` registers folder photos the same way). Its errors are `ServerApiError`s, classified separately from provider errors so they never clear a cloud connection, so a photo is never marked processed without its faces. Face batches are write-only (never read-modify-write), so parallel workers cannot overwrite each other. Deletes/resets are chunked below Firestore's 500-write batch limit.
- **Long-Running Upload Resilience:** Scanner workers never exit on recoverable failures. Expired sessions or upload permission errors pause with `auth_expired` and auto-resume when a new token arrives; Firestore quota pauses with `demand_limit`; transient network/5xx/429 errors retry with exponential backoff, then show `network_error` and auto-retry every 60s. Local `File` objects stay in memory until stored. A screen Wake Lock and a `beforeunload` warning are active while scanning.
- **Parallel Multi-Event Ingestion:** `ScannerContext` tracks scan loops, pause flags, and cancellations independently per event ID (`scanStates` map, `pausedEventsRef`, `cancelledEventsRef`), allowing multiple events to scan in parallel. A warning modal notifies users on event creation during an active scan regarding potential performance impacts.

### 3. Model Accuracy, Mobile Selfie Capture & Clustering Thresholds
- **Detection recall:** Keep SSD MobileNet V1's `minConfidence` at `0.45` for event photo scanning and `0.38` for guest selfie capture to ensure side profiles, mobile camera soft focus, and shadows are successfully detected. Event photos use `detectFacesTiled` (`faceDetection.ts`): a full-frame pass plus a 2x2 grid of 20%-overlapping tiles merged by overlap suppression, because SSD resizes its input to 512x512 and otherwise misses small faces in group photos. Selfies use a single full-frame pass. Changing alignment or the embedding model invalidates stored descriptors of existing events (selfie and event embeddings must come from the same pipeline).
- **EXIF Auto-Orientation & Rotational Fallback:** All uploaded guest files and mobile camera captures are auto-oriented using `createImageBitmap(file, { imageOrientation: 'from-image' })`. If face detection fails at 0°, a rotational fallback sequence (90°, 270°, 180°) is executed on canvas to guarantee detection regardless of phone holding orientation or missing EXIF metadata.
- **Matching precision:** Face matching uses L2-normalized Euclidean distance. Guest selfie matches use a strict threshold of `0.85` (fixed server-side in `api/match.ts`) to prevent false positives. With several faces in a selfie, the largest face is used only if it is at least 1.5x the area of the next one.
